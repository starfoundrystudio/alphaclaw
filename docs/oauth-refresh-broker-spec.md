# OAuth Credentials — Gateway Refresh Broker Spec

**Status:** IMPLEMENTED THROUGH PHASE C 2026-08-26 — all §7 decisions taken by the owner (recorded inline as D1–D6). Phase A is implemented and post-review hardened; the Codex seam, consent-time migration, doctrine, and TeamYou provisioning port are implemented. Live acceptance and the remaining consumer seams are still pending.
**Companions:** `docs/vault-brokered-model-keys-spec.md` (explicitly excluded OAuth/subscription routes), `docs/vault-brokered-channels-spec.md` (Tier S/te covers OAuth _client_ secrets; Tier D covers derived access tokens; this spec covers the class both left open: **user-consent OAuth grants whose durable secret is a refresh token**), and `docs/oauth-broker-v2-consumer-framework.md` (revised 2026-08-27 architecture spike that supersedes this document's original gog seam assumption with owner-created Custom OAuth/OIDC connectors, separated connector-management/token-use capabilities, multi-account grants, and user-defined invocation-time token bindings; not implemented yet).

## 1. Problem

Vault substitution protects static keys that ride requests verbatim. OAuth's durable secret — the refresh token — breaks that model twice: it appears in token-endpoint POST _bodies_ (solvable, S/te-style), and most providers **rotate it on every refresh**, so the _response_ carries a new durable secret that lands on the instance. The vault MITM has no response-capture primitive as shipped, so substitution cannot contain rotation. (agent-vault is open source, so a response-capture primitive _could_ be contributed upstream or added in a fork — see §6a for why the broker is still the better design.) Result: refresh tokens sit in plaintext on instance disks, agent-readable, in stores we already have to defend ad hoc (`openclaw-doctor-oauth-guard` exists solely to shield them from doctor runs).

## 3. Design: refresh broker on the security gateway

Mirror the Phase E custody pattern, applied to token refresh:

- **Durable secret placement.** Refresh tokens live only on the security gateway: root-only files under `/etc/alphaclaw-gateway/oauth-grants/<consumer>__<provider>.json`, sealed under the existing custody KEK (they're on the same host, so KEK-sealing here is belt-and-braces at-rest hygiene, not cross-host custody).
- **The ask is authenticated by workload identity, never a secret.** A dedicated restricted forced-command channel (`alphaclaw-gateway-oauth-broker`, same authorized_keys `restrict,command=` pattern as keystore-custody; per-instance ed25519 keypair issued by the connectivity PKI). Protocol: one JSON request/response per invocation, schema-versioned, mirroring the custody script's conventions.
- **Operations.**
  - `status` → `{ok, grants: [{consumer, provider, expires_at, last_refresh_at}], denied}`
  - `deposit` `{consumer, provider, grant}` → store/replace a grant (used at consent-time migration; grant = refresh token, client credentials where the provider requires them, and the consented `scopes`). Token and revocation endpoints are **not** workload input.
  - `access_token` `{consumer, provider, scopes?}` → broker performs the token-endpoint exchange **from the gateway**, persists any rotated refresh token, and returns `{access_token, expires_at, scopes, scopes_known}`. Caches the current access token until inside a 15-minute validity buffer so AlphaClaw's 10-minute proactive request forces rotation before OpenClaw's five-minute refresh path; earlier repeated asks still reuse the cache. The consumer rejects a deferred response inside its own margin and retries with backoff, preventing a zero-delay loop against an older broker. Phase A accepts an omitted scope request or an exact set match; any attempted narrowing fails closed until provider-specific narrowing is implemented. Initial Phase A records predate the scope field, so they carry `scopes_known: false` during roll-forward. They become known only when the provider returns a scope set or accepts an explicitly transmitted set; caller-only metadata is never promoted.
  - `revoke` `{consumer, provider}` → serialize against refresh, attempt provider-side revocation where the pinned provider contract supports it, then delete the local grant regardless of provider outcome; the response reports the provider-revocation outcome.
  - Deny marker (`oauth-broker-denied`) — same revocation switch semantics as custody.
- **Gateway-owned provider policy.** The exact token endpoint, request encoding and required headers, accepted client identity, permitted parameters, expiry source, and revocation endpoint are pinned per supported `(consumer, provider)` pair in the gateway script. This prevents the compromised workload from turning broker refresh into arbitrary gateway HTTP egress. OpenAI follows the current Codex JSON refresh contract and derives expiry from the access-token JWT `exp`; Anthropic mirrors the pinned Claude Code/Axios request fingerprint; Google uses form encoding. Redirects are rejected rather than followed.
- **Race safety.** `deposit`, `access_token`, and `revoke` take an interprocess lock per grant. A refresh that began before revocation therefore cannot write its rotated grant back after revocation completes.
- **Rotation is contained by construction.** The token-endpoint response never leaves the gateway; the instance sees access tokens only. This is the property substitution cannot provide.
- **Consent flows are unchanged for the user.** Device/paste/browser flows run as today; at the end, alphaclaw `deposit`s the grant to the broker and deletes the local refresh token. The refresh token transits alphaclaw memory once, at consent time — same honest one-shot exposure as entering a key on the approval page.
- **Egress:** the gateway's own token-endpoint calls (`auth.openai.com`, `platform.claude.com`, `oauth2.googleapis.com`) leave from the gateway's public interface — outside the workload NAT flow logs, same as the vault host's provider dials. Note for the Phase 3 inventory.

### Honest threat statement (same discipline as Tier C)

The agent must be able to _use_ access tokens, so a live access token is always readable by a sufficiently capable agent on the instance. The broker protects the **durable** secret: a stolen disk, backup, or snapshot yields nothing that outlives ~1 hour; revocation is one gateway-side action and outstanding access tokens age out; every refresh is a loggable, deniable event at the broker. It does not hide in-flight tokens from the runtime — nothing can. The workload VPS, including `root`, is one trust domain: workload-local ownership and modes are hygiene, not a boundary against the agent. Broker policy, durable grant custody, and revocation therefore remain gateway-enforced.

The crypto is trivial; the seams are not. Each consumer expects a self-refreshing store:

## 5. Interim option: at-rest custody sealing (shippable now, weaker)

Phase E's `alphaclaw-keystore-custody` can seal the OAuth stores today (ciphertext on disk, plaintext in tmpfs). Caveats that make this interim-only: these files are **rewritten on every rotation**, so sealing requires a change-watch + re-seal loop (clunky, race-prone), and runtime plaintext remains agent-readable — it buys stolen-disk/backup protection only, with none of the broker's revocation or rotation-containment. Worth shipping only if the broker slips significantly.

## 6. Prior art — Vercel Connect (and why we don't use it directly)

Vercel Connect (reviewed 2026-08-26) is the hosted incarnation of exactly this architecture: durable grants in a broker, short-lived scoped tokens at runtime, requests authenticated by workload identity (deployment OIDC) rather than a bootstrap secret, rotation contained broker-side, one-command revocation. It **validates the design** and contributes three requirements adopted above: identity-for-the-ask (§3, forced-command keys), rotation containment (§3), and issuance-time scope narrowing (§7 Q4 — request down-scoped tokens where providers support it, something substitution can never do).

Direct use is blocked structurally: (a) instances have no Vercel OIDC identity (Hetzner VPSes can't mint deployment tokens; the SDK's `vercelToken` override targets tests/dev, not a customer fleet) — the only shape is TeamYou fronting Connect, at which point TeamYou is the broker and Connect is a backing store; (b) the credentials that matter most — Codex and Claude CLI subscription auth — use **first-party OAuth clients owned by OpenAI/Anthropic** that cannot be registered as Connect connectors at all; (c) the niche Connect does serve (user-consent connectors for Google/Slack/etc.) is already occupied by Composio in our stack, and would move customer grants into Vercel's control plane (custody posture change) at $3/1k token requests. Same reasoning applies to any hosted broker in this category.

## 6a. Alternative considered: response capture in agent-vault (open source)

agent-vault is open source, so the missing response-capture primitive could be contributed upstream or carried in a fork. Deliberately not chosen: (a) generic response capture turns a stateless substituting MITM into a stateful, OAuth-aware component that must parse per-provider token-endpoint responses, extract secrets, and rewrite bodies — a much larger and riskier primitive than the narrow broker; (b) a fork of a security-critical binary is a permanent maintenance tax (the AlphaClaw hard-fork itself is the cautionary precedent), and an upstream contribution has uncertain timeline and acceptance; (c) even with capture, refreshes would still be _initiated by the instance_ and span two hosts — the broker keeps the entire exchange on the gateway, which is the simpler trust story. Kept open as a future option: if agent-vault later grows a token-custody/unwrap primitive upstream, it could supersede the broker's storage layer without changing the instance-side contract (same note as the channels spec made for the Phase E KEK).

## 7. Decisions (owner, 2026-08-26)

- **D1 — Broker placement: gateway-host service as specced.** Reuses the custody channel pattern, keys, and revocation semantics; no new TeamYou/vault feature.
- **D2 — Scope: all three consumers in one program** (openclaw/codex, claude CLI, gog). Internal implementation order still lands the codex seam first (we own both consent flows) with claude-CLI and gog in the same release train; the claude-CLI store-format drift risk (§4) is accepted.
- **D3 — KEK-seal the gateway grant files: yes.** Same-host hygiene, uniform with Phase E.
- **D4 — Scope narrowing: protocol carries a `scopes` field from day one; no narrowing behavior built now.** Deposits persist the consented scope set, access-token responses return it with `scopes_known: true`, and callers may request the same set. A different set fails closed until provider-specific narrowing exists. Grants written by the initial Phase A bundle have unknown rather than empty scopes; they remain usable by scope-aware callers but stay unknown when a provider does not receive or report the requested set. This is moot for the current consumers (provider-fixed subscription scopes), while keeping issuance-time narrowing available without a protocol rev.
- **D5 — Existing instances: migrate on next consent.** Grants re-home naturally at re-auth/expiry; no active sweep of current auth stores.
- **D6 — Broker unreachable at refresh time: fail closed.** Consumers error until the gateway returns; no instance-side cached-grant fallback (it would reintroduce the durable secret).

## 8. Phases

- **Phase A — protocol + gateway service** (clawctl): **DONE 2026-08-26** (initial implementation main 93ac3fe, then security-review hardening). Broker forced command (`alphaclaw-gateway-oauth-broker`: status/deposit/access_token/revoke, deny marker), PKI keypair, staging both sides (workload install graceful when unstaged), installer script + KEK reuse + restricted authorized_keys entry, verification checks on both hosts. Grant records seal ALL secrets (refresh token + cached access token) under the Phase E KEK — only non-secret timestamps are cleartext. The hardened protocol pins gateway-owned provider endpoints/request/header shapes, rejects redirects and workload-selected egress, carries scopes, best-effort revokes at OpenAI, Anthropic, and Google, serializes refresh/deposit/revoke across processes, policy-normalizes and preserves refresh/access/local revocation for grants written by the initial Phase A bundle, and atomically replaces stale forced-command authorized keys under an installer lock during key rotation. Grant-directory creation, record replacement after provider rotation, and revocation unlink are directory-fsynced before success is reported. The broker identity, pinned gateway host key, and destination remain together in the workload-owned OAuth directory because the workload, including `root`, is not a security boundary. Their purpose is constrained broker invocation and network host pinning; durable-secret containment is enforced by the gateway. Subprocess tests drive the shipping script through rotation containment, caching, at-rest sealing, secret-free status, deny/revoke, provider request/header shapes, expired legacy-grant refresh with a scope-aware caller, corrupt/unsupported legacy revoke, scope enforcement, crash-durability fsyncs, and a real two-process refresh/revoke race. The initial implementation was live-validated on the enforced gateway: script runs sharing the Phase E KEK, deposit → ciphertext-only on disk, TLS certificate verification enforced, status secret-free, revoke; manual drill artifacts cleaned up and gateway restored. Revalidate the hardened provider contracts during Phase B seam acceptance. Provenance-stamped bundle → beta pin → soak still pending the seam.
- **Phase B — codex seam** (alphaclaw): **IMPLEMENTED 2026-08-26.** Browser callback, paste, and device consent flows atomically journal and deposit before committing the local profile and fail closed on deposit failure. Startup reconciles a crash in either half of that transaction: a brokered SQLite profile with the journaled access-token hash completes publication before rotation, while an uncommitted grant is revoked. Managed profiles contain only a short-lived access token, expiry, account metadata, and a versioned non-secret broker marker; a managed host never falls back to local refresh-token storage when staging is absent or incomplete. Generic model-auth APIs reject Codex/OpenAI OAuth writes and deletes so they cannot bypass broker deposit or revocation. A single-flight proactive loop refreshes ten minutes before expiry, refreshes on boot before gateway startup, retries failures after one minute, and checks broker/grant health every five minutes. Refresh, reconnect, disconnect, and recovery share one lifecycle serialization point. Broker commit enumerates configured agents and exact raw paths for every on-disk agent directory, mutates each latest SQLite row under `BEGIN IMMEDIATE`, removes every Codex/OpenAI OAuth sibling and its state/config references while preserving OpenAI API keys, and durably records physical sanitization before committing a replacement row. It then checkpoints/truncates WAL and vacuums databases that previously held a durable refresh token; a busy checkpoint, failed vacuum, or crash leaves that non-secret marker pending so recovery cannot forget the physical cleanup after the logical row contains only the broker marker. It also scrubs active legacy `auth.json`, shared `credentials/oauth.json` at OpenClaw's configured `OPENCLAW_OAUTH_DIR`, canonical, sibling, and orphaned Codex OAuth sidecars while preserving sidecars referenced by surviving credentials, and every pinned OpenClaw-generated full-store backup family after the broker marker is durable; operator-created backups are not guessed at or deleted. OpenClaw's `secrets.reload` RPC publishes each change into its process-local runtime snapshot. Consent finalization, access-token refresh, and removal each have distinct durable publication journals; a managed child that is still starting leaves the appropriate journal pending, and gateway-ready handling republishes the current access profile or completes removal without waiting for the next refresh timer. Dashboard status distinguishes healthy, refreshing, degraded, expired, unavailable, and reconnect-required states. Disconnect always journals and sweeps the complete local artifact set even when the primary profile is absent; it attempts live publication and gateway revoke independently so a post-commit cleanup failure cannot leave the runtime snapshot live, and retains the closeout journal until every step completes. The doctor guard ignores broker markers. Only genuinely unmanaged installs retain the legacy local-refresh path.
- **Phase C — migration + doctrine**: **IMPLEMENTED 2026-08-26.** Existing local grants migrate on their next successful consent. The managed-instance doctrine directs subscription OAuth through dashboard connect/reconnect and identifies the marker as an intentional working value. Successful SQLite persistence retires the legacy JSON duplicate.
- **Phase D — remaining consumers** (claude-CLI and gog seams, per D2 all in this program; codex lands first as the pattern-prover within the same train). **Object model approved; owner management plane proposed 2026-08-27:** do not implement the original proactive-store rewrite. `oauth-broker-v2-consumer-framework.md` defines connector/grant/binding and generic lease-exec boundaries. `oauth-broker-v2-management-plane.md` proposes TeamYou-signed owner entry followed by browser-direct gateway connector management and gateway-owned consent/callback/code exchange, with no enrollment capability crossing the workload. Owner review of that management contract is the next gate; production code and a new host-asset bundle have not been created yet.
- **TeamYou port**: **IMPLEMENTED 2026-08-26** on `codex/oauth-broker-provisioning`. It mirrors the hardened clawctl broker asset byte-for-byte, provisions a dedicated PKI identity, stages the private/public halves on the workload/gateway respectively, installs the forced command with atomic key rotation under the shared authorized-keys lock, and verifies both the restricted workload channel and gateway-local empty-grant state.

## 9. Release gate and live acceptance

Do not promote the bundle solely from unit tests. On a freshly provisioned enforced test instance:

1. Confirm workload `status` succeeds only through the restricted identity and returns no secret fields; confirm direct shell/forwarding attempts fail.
2. Complete a fresh Codex consent and verify the broker reports the fixed `openclaw-codex/openai` grant while recursive workload scans (including every agent SQLite file and `-wal`) find neither the refresh token, a sibling OpenAI OAuth profile, an active legacy auth/OAuth store, a legacy OAuth sidecar, nor any pinned OpenClaw-generated full-store backup.
3. Restart AlphaClaw and OpenClaw, confirm refresh-on-boot updates SQLite before gateway startup, and complete a real model request. Then trigger a post-start refresh and confirm `secrets.reload` publishes the new token without a gateway restart.
4. Force a broker refresh through the real OpenAI contract, confirm any rotated refresh token remains gateway-only, then complete another model request.
5. Deny or temporarily break the broker channel and confirm status becomes degraded/expired without restoring a local durable secret; restore it and confirm automatic recovery.
6. Disconnect once with the gateway available and once while it is unavailable. In both cases the workload profile must disappear immediately; after restoration, the pending revoke must clear automatically.
7. Pin the provenance-stamped clawctl, AlphaClaw, and TeamYou revisions into one beta bundle and soak it before beginning the Claude CLI and gog seams.
